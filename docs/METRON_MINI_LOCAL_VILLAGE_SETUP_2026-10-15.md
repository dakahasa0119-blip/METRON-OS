# 同じPCでの新村作成とプロジェクト準備

この追加は、利用者が新しい村のID、保存先のフォルダー名、引き継ぐ情報を確認してから、同じPCに独立した村を作るためのものです。利用者の承認後、実Runtimeと隔離ブラウザーで作成・配達・停止再開・保存状態の読み戻しを確認しました。検証の範囲と残る接続は下に記します。

## 新村の範囲

新村一つに `MetronMiniRuntime` 一つを割り当て、その中に母艦A/BとGatewayを持ちます。既存の村1/村2の保存ファイルを新村の保存先として使いません。作成した新村は既存の管理画面で操作します。後続の追加接続では、所有者が作成した新村を仕事・登録済みプロジェクト修復・Village Squareへ参加させます。選択した継承参照と新村での採用を区別し、各操作には現在の所有者接続と明示的な判断が必要です。手順と最新の検証範囲は[新村から仕事・BAKU修復・Rumor共有へ進む](METRON_MINI_DYNAMIC_VILLAGE_FLOW_2026-10-15.md)を参照してください。

起動は現在のMini親プロセスが所有する一時的なNode子プロセスです。IPCだけで固定のRuntimeを操作し、新しい待受ポートや自動起動設定は作りません。既定の稼働上限は5分です。親の停止、IPC切断、上限到達時には停止を試み、終了を確認できない場合は明示して再起動を止めます。恒久的なサービス登録、別PCへの展開、外部AI接続は含みません。

## 起動前の設定

```powershell
$env:METRON_MINI_DATA = '<absolute-path-to-dedicated-mini-data>'
$env:METRON_VILLAGE_BASE = '<absolute-path-to-owned-local-village-folder>'
node mini/start.mjs
```

`METRON_VILLAGE_BASE` を省略するとMiniデータ領域の `created-villages` を使います。各新村の保存先は、その配下の利用者が選んだ単一フォルダーです。Miniの管理用 `village-bootstrap` とは分離します。`METRON_VILLAGE_BOOTSTRAP=0` なら新村機能を無効にできます。

起動ログの所有者用 `/experience#project-operator=...` URLを同じPCで開きます。この起動専用のキーを他人に共有しないでください。従来のプロジェクト画面と同じ所有者キーを使用し、読み込みや再起動だけでは新村の作成・起動を行いません。

## 新村の操作

1. 引継元の村と、必要なら保存済みの仕事を選びます。新村ID、フォルダー名、表示名、目的を入力します。IDとフォルダー名はそれぞれ重複できません。
2. 目的、配達済みの元メッセージ、採用済みの知識を個別に選び、プレビューで本文、出典、ハッシュ、実際の保存先を確認します。選択していない知識は引き継ぎません。
3. 内容を確認して「作成」を行います。この段階は種とマニフェストの保存だけです。新村の起動は別の確認操作です。
4. 「起動」で固定Runtimeを開始します。「ローカル送信」は短い本文をその村のAからBへ送り、Gatewayと母艦の保存状態を表示します。AIへの送信操作ではありません。
5. 「停止」後、保存内容を読み戻せます。親を再起動した場合も自動では子を起動しません。中断状態では終了確認と明示的な再開を必要とします。

引継ぎは許可した本文と出典フィールドの抽出です。元の仕事全体、認証情報、環境変数、所有者キー、worker lease、外部送信や適用への同意は複製しません。選択する本文そのものに個人情報や秘密が含まれないかは、利用者がプレビューで判断します。

同じ要求IDと同じ内容の再送は以前の結果を参照します。内容を変えた同じID、別の要求による同名作成、所有を確認できない保存先は拒否します。作成中断や取り消しでは既存ファイルを消しません。画面で保存状態を確認し、明示的に再開します。結果が不明な送信を自動再送しません。

Runtimeの対象ソースのハッシュも記録します。作成時とコードが変わった場合は、そのまま既存の新村を起動せず、対応する版と保存内容の確認が必要です。

## 初回プロジェクト準備を画面から行う

初回は引き続き所有者が、修理対象の小さな信頼済みGitリポジトリ、固定した40桁commit、編集許可、公開テスト、適用後テスト、対象ソースと分離した非公開テスト、専用の空の割当先を決めます。これらの判断を済ませた後の3つの作業領域作成を、画面の一操作に移します。

従来の `METRON_PROJECT_REGISTRY` と別に、所有者が次の10フィールドを持つslotの配列をUTF-8 JSONで保存します。最大8件です。下記の山括弧は所有者が選んだ絶対パス、commit、相対ファイル名に置き換えます。

```json
[
  {
    "id": "owned-project",
    "label": "所有者が確認した対象",
    "repositoryRoot": "<absolute-source-repository>",
    "baseCommit": "<40-lowercase-hex-commit>",
    "allowedEdits": [{"path": "src/value.mjs", "operations": ["edit"]}],
    "publicTests": ["tests/public.test.mjs"],
    "postApplyTests": ["tests/smoke.test.mjs"],
    "acceptanceRoot": "<absolute-independent-sealed-root>",
    "acceptanceTests": ["owner.test.mjs"],
    "allocationRoot": "<absolute-dedicated-empty-allocation>"
  }
]
```

```powershell
$env:METRON_PROJECT_SETUP_MANIFEST = '<absolute-path-to-owner-setup.json>'
node mini/start.mjs
```

所有者画面でslotと範囲を読み、独立した確認欄を選んで準備します。固定commitから `allocationRoot/b`、`c`、`a` の3つのdetached Git worktreeと、証拠 `e`、一時領域 `t` を作成します。準備完了後に登録済み対象へ表示されます。準備自体はテストやAIを実行しません。候補作成などは既存の別操作です。公式CLIを使う場合は、従来どおり所有者が `METRON_CODEX_EXECUTABLE` を設定します。

ブラウザから任意のパスやコマンドを登録できません。元リポジトリは追跡対象だけのcleanな状態を必要とし、非公開テストは全slotのソース・割当先から分離します。従来の登録済みプロジェクトとの混在でも、ソース・非公開テスト・割当先の境界をMiniデータ作成前に検査します。同じ元リポジトリの共有は許します。準備でclone、fetch、pack、remote、拡張のインストールを実行しません。Git hooks、fsmonitor、system/user attributesを準備コマンドで抑止し、対象の `.gitattributes`、共通Git領域のattributes、外部object storeやpartial cloneを拒否します。一般の既存登録経路全体を未知コードのsandboxにするものではありません。

`ready` の永続化が成功してから画面側の登録を有効にします。途中の失敗や親停止では所有済み作業領域と履歴を残し、`requires_owner_reconciliation` として自動再試行しません。ホスト側で状態を調べてから整理します。再起動時は保存済みのreadyを検証して読み戻します。

### 承認後の実Runtime確認

利用者が試験用追加flagの解除を承認した後、基点 `997c42c` と保存済み29ファイルのハッシュ一致を確認し、同じ固定第一者Runtime、限定した環境変数、IPC、有限時間で再開しました。

最初はfocused 4/6でした。専用領域内のジャンクション作成がsandboxで `EPERM` となり、正式な昇格で同じ試験を実行すると5/6になりました。別のパス・リンク方式・Windows設定へ置き換えていません。残るIPC切断の失敗は製品側の終了確認でした。

- 修正後のfocusedは6/6、HTTPは3/3、隔離Chromiumは2/2成功。各Nodeプロセスの実終了コードは0、実行中の凍結ソース変更は0でした。

- 追加の別領域では、製品の `startMini` を異なる親Nodeプロセス3つで順に起動・実終了しました。最初に選択した目的・元本文を保存し1件配達、次の親で読み戻して明示起動後にもう1件配達、最後の親ではPOSTなしでBの同じ2件を確認しました。各親の終了コードは0で、元村のファイルも不変でした。PC全体の再起動は行っていません。
