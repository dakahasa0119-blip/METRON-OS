# 保存した修復候補の検査を再計算してPoUCへ残す

## 根拠と今回の範囲

[Mini完成基準D12](METRON_MINI_COMPLETION_CRITERIA_2026-10-14.md#d-修復知識の共有と有用計算)は、修復候補の有用な検査を別途再計算し、PoUC記録を照合して、重複や改ざんを成功として数えないことを求めます。同文書は通貨・現金報酬・本格的マイニングをMiniの完成条件から外しています。[既存PoUCの範囲](AI_POUC_RECOVERY_EXECUTION_2026-10-14.md#pouc--proof-of-useful-computation)は、構文・DNA監査を実行して結果を再計算するものです。

従来の手入力コード用PoUCは保持し、登録済みプロジェクトの実際の修復検証と結ぶ操作を追加しました。候補を生成したAIとは別に、所有者が登録した固定検査を再実行します。新しいAI送信・インストール・課金・コード適用・報酬は行いません。原構想への参照は[README](../README.md#original-concept-documents)にあります。原Gist本文は今回取得できず、未取得の本文に追加要件があるとは推定していません。

## 利用者の操作

1. `/experience` で所有者接続を行い、登録済みプロジェクトの検証済み仕事を選びます。新村の場合は、その村を明示起動します。候補は独立検証済みである必要があります。
2. 「有用な検査を再計算して残す（PoUC）」で表示中の候補を確認し、確認者名とチェックを入れて実行します。候補commit・差分・検証IDを固定して送ります。
3. ホストは、その候補の登録済み公開検査と非公開受入検査をそれぞれ1回、既存の隔離検査器で実行します。各検査の実行上限は30秒で、固定された入力が実行前後で変わっていないことも確認します。
4. 元の検証と再計算の入力証拠・成功件数が一致した場合だけPoUC台帳へ保存し、仕事・村・セッション・元の検証へ結び付けます。出力中の時刻などは変動するため、ログ全体のハッシュ一致は求めず、両回のハッシュを保存します。非公開検査の本文・生ログ・パスはPoUC台帳へコピーしません。
5. 必要なら、表示された記録識別子と適用条件・限界を、既存の公開用要約本文へ人が記入し、別の確認操作でRumorを公開します。受信村は従来どおり明示採用または隔離します。採用済み知識は公開した本文、元の候補・検証来歴、親Rumorを保持します。

共有形式は拡張していません。識別子を本文に記入する行為は、その台帳の配布や受信側の独立再計算を意味しません。公開済みRumorは後から書き換えず、公開後に追加したローカルPoUC記録も自動追記しません。必要な記録を含めて共有する場合は、公開前に再計算と要約確認を行います。

## 保存・再開・重複の扱い

- `mini/project-pouc.mjs` は、登録・候補・差分・固定検査入力・件数から計算の識別を作ります。日時や実行ログの変動で同じ計算を別件として再加算しません。台帳は1000件までです。
- `project-sessions/project-pouc-ledger.json` には正規化した元の検査と再計算結果、入力・出力ハッシュ、計算と証拠のdigestを保存します。仕事の識別・村・セッション・検証との対応は、別に検証されるセッション記録と仕事の保存記録に残ります。
- 起動、GET、画面更新は保存済み証拠を読み直すだけです。同じ検証の記録が保存済みなら、明示要求を繰り返しても固定検査を再起動せず既存記録を返します。
- 成功するまでの明示再計算は同じセッションで最大3回です。失敗・skip・未終了・入力や件数の不一致は成功記録になりません。実行中に親が止まった記録は、終了未確認として停止し、自動再実行しません。
- 再計算中は同じセッションの適用などを進めず、その仕事の共有準備・公開も拒否します。終了後は最新の仕事を読み直し、保存済みの共有内容を上書きしません。
- JSON台帳は既存Miniと同じ単一writer前提です。複数の親Nodeで同じデータ領域を同時更新する分散トランザクションではありません。

PoUCの再計算成功は、登録された固定検査について一致したという証拠です。未知の全障害の修復、発信者の認証、受信村での独立検証、分散計算の信頼性、本番適用を保証しません。受領記録の `productionRepairVerified` と `distributedTrust` はともに `false` です。

## 検証の区別

新接続では、ローカル台帳、実Gitと固定Node検査、DOM/API試験、隔離Chromiumの実DOMを分けて検証します。修復候補を作る統合fixtureは試験用と明示したworkerであり、本物のAIではありません。過去の実Codex1件の成功や425件のWindows回帰を、新しいPoUC接続の実AI・Linux成功証拠へ流用しません。

対象試験は台帳7/7、画面単体17/17、実Gitと固定Node検査の接続2/2、隔離Chromiumの既存新村フロー1/1が成功しました。ブラウザ初回はサーバー保存から画面表示への反映待ちが不足して失敗し、保存状態と画面の同一digestの両方を待つよう試験を修正して、別の隔離領域で成功を確認しました。

続くWindows全件試行は40分の固定枠で終了し、TAPには350件（成功348・失敗2）が残りました。実際の終了は時間切れのSIGTERMで、全件footerはありません。実行中の159ソースファイルの変更はゼロでした。

失敗した既存ブラウザ試験は、村選択欄の操作可能状態を待たずに変更イベントを送っていました。選択欄と後続の仕事・知識・受信本文が操作可能になるまで待つよう試験を修正し、単独で成功しました。HTTP試験は外側の60秒枠に達し、180秒へ変更した再実行では試験用clientの20秒待ちに達しました。固定検査を待つ `start` / `validate` だけclientを120秒とし、通常要求の20秒、製品の検査上限30秒、元のassertionを維持して、該当1件の成功・終了コード0を確認しました。先行した失敗記録も保持しています。

未完了だった16ファイルは別実行で84/84成功、終了コード0、skip・取消ゼロでした。補完実行とHTTP再実行でも実行中のソース変更はゼロです。最初の350件、修正後の2対象、補完84件を区別した分割検証では434種類の成功を確認しています。これは最終HEADを単一の全件実行で完走したという記録ではありません。PoUC接続後の製品ソースは変更せず、最終変更は試験の待ち条件・時間枠とCI・文書に限定しています。

Linuxの既存CIはNode 24、Git、検出済みChromiumを用います。村ブラウザ試験も実行するため `METRON_RUN_VILLAGE_BROWSER=1` を指定します。Windows全件試行が40分で未完了だった実測を踏まえ、job上限を60分にしました。これは実行経路の準備であり、Linux実行や新PoUC接続の実AI成功を意味しません。

通常ログイン済みChatGPTのARC、別の実AIへの代替、PC全体の再起動、一般的な未知故障修復は引き続き別の完成ギャップです。
