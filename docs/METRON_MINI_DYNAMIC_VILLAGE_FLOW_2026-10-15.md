# 新村から仕事・BAKU修復・Rumor共有へ進む

この追補は、同じPCで明示的に作成した新村を、既存の仕事・登録済みプロジェクト修復・Village Squareへ接続する使い方です。新村には独立した母艦A/BとGatewayがあり、作成・起動・修復候補の要求・適用・共有・採用はそれぞれ別の操作です。

初期設定とGit作業領域の準備は[同じPCでの新村作成とプロジェクト準備](METRON_MINI_LOCAL_VILLAGE_SETUP_2026-10-15.md)、修復対象の登録と検査の考え方は[仕事画面の利用手順](METRON_MINI_PROJECT_USER_FLOW_2026-10-15.md)を参照してください。登録済みの修復対象、固定commit、編集許可、公開・非公開検査は引き続き所有者が用意します。

## 1. 継承内容を確認して新村を作る

所有者が現在の起動で発行された所有者用URLから `/experience` を開き、「新しい村を準備する」へ進みます。

1. 新村ID、専用フォルダー名、新村の目的を指定します。表示名やIDは村の識別、目的はその村で行うことです。元の仕事の目的と同一である必要はありません。
2. 元の村と、必要なら保存済みの仕事を選びます。「元の目的」「元の受信本文」は別々の選択です。知識も必要な項目だけを選びます。
3. プレビューで新村ID、保存先、新しい目的、選んだ本文・知識・出所を確認し、確認欄を選んで作成します。選択を変えた場合は、プレビューと確認をやり直します。
4. 作成直後は起動していません。保存された村を選び、現在の状態を確認してから「この村だけを起動」を押します。

起動時、**継承する受信本文を選んでいた場合だけ**、その本文を新村の母艦AからBへ配送し、仕事の元に選べる観測を1件作ります。同じbundleの明示的な再起動では同じ観測の識別を使い、配送済み本文を新しい観測として増やしません。本文を選んでいない場合は、必要な本文を「この村の母艦へ一回送信」で明示的に送れます。この配送自体はAI呼出しではありません。

引き継ぐのは選択した本文と出所です。元の目的、選んだ知識、その出所・修復証拠の参照は、新村で検討するための参考情報になります。**元の村で採用済みだったことを、新村自身が検証・採用済みであることへ読み替えません。** 選ばなかった知識、認証情報、環境変数、所有者キー、worker lease、外部送信や適用への同意は継承しません。

## 2. 新村の仕事を保存し、登録済み対象を修復する

新村が起動中なら「この村の仕事へ」を押せます。仕事の村がその新村へ切り替わり、保存済みの仕事、なければ継承した目的や新村の目的が入力の候補になります。目的を確認し、配送済みの観測と必要な参照知識を選んで仕事を保存します。

新村の仕事・修復・Rumorに関する変更操作には、**現在の所有者接続と、その村が実際に起動中であること**が必要です。停止中の村は保存状態を読めますが、古い接続や保存済みの許可だけで仕事や修復を実行しません。

登録済みプロジェクトの修復は、既存の仕事画面と同じ順序で進めます。

1. 所有者が準備した対象を名前で選び、編集対象、検査の境界、使い捨て適用先、送信される内容を確認します。
2. 対象と範囲の確認後、固定された公開検査で問題を再現します。新村の目的や継承本文から、任意のパス・コマンド・編集権限を追加することはありません。
3. 次の候補を要求するたびに、**今回1回の外部Codex送信と費用について新しく同意**します。新村の作成・起動、前の実行、元の村の同意は代用になりません。
4. 実際の差分を独立に読み、確認した候補を固定して公開検査とホスト側の非公開検査を実行します。非公開検査の内容をworkerへ渡しません。
5. 検証済み候補・現在のHEAD・適用先を改めて確認し、登録済みの使い捨て作業領域だけへ適用します。適用後検査と保存状態の読み戻しを確認します。

AIの返答やworkerの成功報告だけでは、検証済み・適用済みになりません。登録範囲外の修復、本番や元checkoutへの反映、任意の未知プロジェクトの修復を許可する経路でもありません。公開検査の失敗は保存したうえで次の候補を明示的に要求でき、非公開検査で拒否された候補はその結果をworkerの修正材料にしません。

## 3. 修復結果をRumorとして共有し、受信側で判断する

検証済みの仕事では、共有文、確認した診断、適用できる条件、限界・未確認点を確認して「共有案を手元に保存」を押します。保存した下書きには、送り元の村・仕事・候補commit・差分・検査などの来歴が結び付きます。下書きの保存は公開の許可ではありません。

公開するRumorの内容と証拠を確認してから、別の確認操作でローカルのVillage Squareへ公開します。送信元・受信先の選択には、登録された新村も表示されます。新村を含む操作では、関係する新村の起動状態と現在の所有者接続を確認します。

受信側はGatewayで受け取った後、**採用するか、隔離するかを明示的に判断**します。配送完了は採用ではなく、採用は修復の自動適用でもありません。採用した知識を次の仕事へ使う場合も、その仕事で項目を選びます。送り元の検査証拠や継承時の参照情報は保持しますが、受信側が同じ条件で独立に検証したという主張にはなりません。

## 4. 停止・再開・結果不明の扱い

村を止める前に、仕事と修復workerの状態を確認します。検証・適用などの処理中には、村の停止を受け付けない場合があります。

「この村だけを停止」では村のchildを停止し、関連する修復workerがあれば停止を要求します。**停止要求を送れたことと、workerが実際に終了したことは別です。** 村の終了確認に加えて、仕事画面の終了状態・実終了コード・終了未確認の記録を確認してください。関連セッションの停止要求が拒否された場合や、終了が未確認の場合は、その表示を残して所有者が確認します。新しいworkerや同じ保存先のchildを重ねて起動しません。

親Miniを再起動した後は、まず画面のGETで保存された村・仕事・参加台帳を読み戻します。再起動時の中断状態の照合や所有者の再接続は、操作を再実行する同意ではありません。childを自動起動せず、観測やRumorを自動で再配送せず、AI呼出しや候補の再試行もしません。停止済みの同じbundleを使うには、状態を確認してから明示的に起動します。中断・終了未確認は、自動復旧の成功として扱いません。

## 保存を担当するプロセス

新村の母艦A/B・GatewayのRuntimeは、その村のchildが一つだけ書き込みます。親は別の参加用台帳に、村の識別・選択した継承参照・知識・仕事・Rumorの来歴を保存します。親がchildのRuntimeファイルをもう一つのwriterとして直接更新する構成にはしていません。実配送はIPCでchildへ依頼し、保存結果を読み戻して確認します。

この区別により、村が参加台帳に載っていること、childが起動中であること、仕事の実行や修復workerが終了したことをそれぞれ確認できます。単に一覧に名前があるだけで、操作可能・修復済みとは判断しません。
